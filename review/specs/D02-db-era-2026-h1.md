## 1. Era narrative

This era sits between the 2025 bootstrap (unit D01, which ended with the 2025-11-20 "Remove ALL RLS restrictions" arc) and the 2026-06 security rebuild (unit D03). Five phases are visible in the file sequence:

1. **January — feature build-out sprint.** New subsystems land almost daily: inspection signatures (20260108042823), site asset register + `asset_category` enum (20260109105319), PDF report templates with seeded defaults (20260110132516), an OAuth API surface for external apps (20260110172925), COC extraction v2 (20260113062616), site schematics + block mapping (20260120132425), and client magic links (20260122090622). Public/QR surfaces are powered by blanket `anon SELECT USING (true)` policies added in three waves (20260108071956, 20260109084016:5-8, 20260123052442). The access-link tracking design is reworked three times in 75 minutes on 2026-01-23 (20260123052554 → 20260123052614 → 20260123052657).
2. **February — auth/onboarding modernisation + spot writes.** Auto-logout settings (20260206105621:2-4), `profiles.onboarding_completed` plus a `handle_new_user` default-role fix (20260214023114), visitor registration for magic links (20260217082506), contractor inspection write policies (20260219090420), and a one-off in-migration password reset for a named user (20260212144831).
3. **March–April — COC local validation v3 + offline photos, then RLS flattening.** The "strict empirical engine" table `coc_local_validations` (20260309172544:2-3) grows 33 Annexure-1 columns (20260310075810:4-35); `coc_compliance_photos` + the `coc-photos` bucket (20260310083442) and the polymorphic `offline_photos` table (20260310085611) arrive; then 20260406131029 replaces role-scoped policies on 7 tables with a single `"All authenticated users full access"` `USING (true)` policy each — an in-era repeat of the 2025-11 loosening pattern.
4. **April–May — out-of-band-flavoured additions.** `contractor_coc_uploads` (20260410013045:12-22) and the inspection auto-link/relink-audit system (20260519045946) are later described by 20260611100000:6-7 as "created out-of-band (via the dashboard, not in supabase/migrations)" — yet both exist as tracked migrations; both files entered git on 2026-05-25 in the bulk commit `109e0ee "chore: integrate Lovable's 84 commits worth of substantive changes"` (git log --follow).
5. **2026-05-25 — convention break.** `20260525120000_auth_events_audit.sql` is the first human-named migration (header: ported from ESITE.V1, POPIA §16/§24 rationale, 20260525120000:3-10). Every earlier file in this unit uses the Lovable `<timestamp>_<uuid>.sql` convention.

Character of the era: 18 tables created (6 of them destroyed one month later by D03's feature razor), heavy data-repair DML with hardcoded production UUIDs, and an RLS posture that both opens (anon reads, `USING (true)` writes) and locally tightens (20260113062636, 20260313070142) without a consistent model — the inconsistency D03 explicitly remediates (20260610120000:1-11).

## 3. Security posture changes

**Opened during this era:**

- **Blanket anon reads.** `FOR SELECT USING (true)` policies with no role qualifier (hence anon-reachable) on: subsections, sites, clients, document_categories, site_documents (20260108071956:5-32); snags (20260109084016:5-8); site_schematics + schematic_blocks ("Anyone can view …", 20260120132425:34-37,55-58); coc_validations, inspections, floor_plan_pins, subsection_floor_plans, and conditionally subsection_documents/site_documents/inspection_templates (20260123052442:4-73); client_access_links ("Public can select access_links for validation", 20260123052614:9-12); site_assets `TO anon` (20260217085025:3-7); storage "Anyone can view COC photos" `TO public` (20260310083442:71-74).
- **Role-unqualified writes.** access_link_visitors anon INSERT of PII `WITH CHECK (true)` (20260217082506:20-22); contractor_coc_uploads SELECT/INSERT/UPDATE all `(true)` with no `TO` clause (20260410013045:26-33); inspection_relink_audit "Service inserts relink audit" `WITH CHECK (true)` (20260519045946:23-25).
- **Blanket authenticated writes.** site_assets full CRUD `TO authenticated` `(true)` (20260216054714:2-28); the 20260406131029 flattening: role-scoped policies dropped and replaced by `"All authenticated users full access" FOR ALL TO authenticated USING (true)` on coc_compliance_photos (:5-14), offline_photos (:19-28), floor_plan_pins (:33-42), document_categories (:50-59), inspection_items (:66-74), inspection_signatures (:79-88), floor_plan_pin_comments (:93-102).
- **Anon-facing SECURITY DEFINER with role switching.** validate_access_link v2 calls `set_config('role','postgres', true)` before its UPDATE (20260123052614:31) — replaced the same morning by v3 without it (20260123052657:1-5).
- **Secrets in history.** A bcrypt-wrapped but plaintext-source password `'Marries@001'` for a real account email (20260212144831:12,19); OAuth client secrets and access/refresh tokens stored as plaintext hex TEXT columns (20260110172925:5-6,19-20).

**Tightened during this era:**

- coc_extractions: three permissive policies dropped and replaced (20260113062636:3-38) — though the replacements' predicates (`extracted_by IS NULL` passes anon :12; UPDATE/DELETE use existence-only EXISTS with no `auth.uid()` :15-38) are precisely what 20260610120000:9-11 later names as Vuln.
- client_access_links table itself is Admin-managed only (20260122090622:27-36).
- schematic_blocks write policies re-targeted from implicit-any-role to `TO authenticated` (20260313070142:2-23; partially repeated by 20260313095510:2-8).
- api_clients Admin-only; api_access_tokens/api_request_logs service-role-managed (20260110172925:47-74).
- auth_events: service-role-write-only (no INSERT policy), user-reads-own SELECT (20260525120000:44-53).
- coc_local_validations, coc_compliance_photos, offline_photos start with role-scoped Admin/User/Contractor/own-rows policy sets (20260309172544:46-69; 20260310083442:29-58; 20260310085611:24-53) — the latter two flattened a month later by 20260406131029.

## 5. Observations (factual, no judgment)

1. 20260212144831:12,19 embeds a real user email and the plaintext source password `'Marries@001'` in permanent git/migration history; the helper function is dropped in-file but the literal remains in every clone.
2. The era's blanket anon-read policies (11+ tables) are never dropped in the tracked migration history; D03 defers this to a "Phase 3" (20260614100000:4) that has no migration file, and records that the equivalent prod cleanup happened via the SQL editor out-of-band (20260614110000:5-8).
3. validate_access_link v2 executes `set_config('role','postgres', true)` inside an anon-callable SECURITY DEFINER function (20260123052614:31); it was replaced the same morning (20260123052657:1-5 says role switching "is not allowed").
4. 20260611100000:6-7 describes contractor_coc_uploads and inspection_relink_audit as created "out-of-band (via the dashboard, not in supabase/migrations)", yet both are created by tracked migrations in this unit (20260410013045:12, 20260519045946:8); git shows both files entered the repo on 2026-05-25 in one bulk integration commit (`109e0ee`) — i.e. the migration files post-date the schema they describe.
5. 20260406131029 replaces role-scoped RLS with `USING (true)` full-access-for-authenticated on 7 tables; on the 5 of those tables that still exist, those policies are still in place (no later drops found).
6. contractor_coc_uploads' three `(true)` policies carry no `TO` role qualifier (20260410013045:26-33); anon reach was later closed by grant REVOKE, not policy change (20260611100000:24).
7. access_link_visitors accepts anonymous INSERT of name/email/phone PII with `WITH CHECK (true)` (20260217082506:20-22); no later migration modifies this table.
8. inspection_signatures' SELECT policy predicate is an EXISTS over inspections⋈sites that never references `auth.uid()` (20260108042823:23-29), so it is satisfied for any row whose inspection exists.
9. The 20260113062636 "more restrictive" coc_extractions rewrite has an INSERT check that anon passes (`extracted_by IS NULL`, :12) and UPDATE/DELETE predicates that reference no principal (:15-38) — the exact wording later quoted as a vulnerability by 20260610120000:9-11.
10. Production UUIDs are hardcoded in repair DML: inspection `d4b630cf-…` (20260108121126:10, 20260108121329:10) and six subsections with shop-name comments (20260201150950:6-12,17), making these migrations environment-specific.
11. The 20260114082530 CHECK constraints institutionalise duplicate mixed-case status vocabularies ('Approved'/'approved', 'Failed'/'rejected'…) on subsection_documents (:11-22); normalisation only happens in D03 (20260612140000, 20260725100000).
12. The `coc-photos` bucket (public=true) and its three storage.objects policies (20260310083442:61-79, delete policy replaced 20260310085611:57-69) outlive the coc_compliance_photos table dropped by 20260612130000:8 — no 2026-06/07 migration references `coc-photos` (grep = 0 hits).
