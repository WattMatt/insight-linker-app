## Unit header

**Unit purpose (as-is).** Five self-contained Deno edge functions that form the app's external API surface for two integrations: the "DocBuilder"/"PDFMaker" template exchange (templates, save-template, template-sync — all operating on the `inspection_templates` table) and an OAuth2-style report API for third-party clients (oauth-token issues tokens against `api_clients`/`api_access_tokens`; api-reports serves report data guarded by those tokens). None of the five is invoked by in-repo application code; callers are external systems.

**Module-level observations (verified).**
- No file contains an `export` statement; each file's entire surface is one HTTP handler — `Deno.serve` in templates/index.ts:338 and save-template/index.ts:8, `serve` from `https://deno.land/std@0.168.0/http/server.ts` in template-sync/index.ts:1,107, api-reports/index.ts:1,38, oauth-token/index.ts:1,10. All import `createClient` from `https://esm.sh/@supabase/supabase-js@2` (line 1 or 2 of each file).
- All five create their Supabase client with `SUPABASE_SERVICE_ROLE_KEY` (templates:376-378, save-template:35-37, template-sync:113-115, api-reports:44-46, oauth-token:16-18), so table access bypasses RLS.
- All five are declared `verify_jwt = false` in supabase/config.toml (unit D04): templates :30-31, save-template :33-34, api-reports :39-40, template-sync :42-43, oauth-token :58-59. Each therefore implements its own auth: `DOCBUILDER_PUBLIC_TOKEN` bearer check in templates (fail-closed, constant-time digest compare, :344-374) and save-template (fail-open plain compare, :14-23); `DOCBUILDER_SYNC_KEY` bearer check in template-sync (fail-open, :11-30); DB-backed token/credential lookup in api-reports (:11-36) and oauth-token (:32-68).
- All five send `Access-Control-Allow-Origin: *` CORS headers and answer OPTIONS preflight with the bare CORS headers (templates:3-6,339-341; save-template:3-6,9-11; template-sync:4-8,108-110; api-reports:4-8,39-41; oauth-token:4-8,11-13).
- All five wrap the handler body in try/catch and return a JSON 500 carrying `error.message` on unexpected failure (templates:538-545, save-template:104-111, template-sync:347-354, api-reports:284-291, oauth-token:114-121).
- Zero test files exist for the unit: `git ls-files 'supabase/functions/*' | grep -i test` → no matches; no src test references any of the five names (grep over `*.test.*`/`*.spec.*` → no matches).

**External contract.** The rest of the app gets: (1) nothing at import level — no src or supabase file imports from these directories; (2) shared state via the `inspection_templates` table, which the three DocBuilder functions write/read with service role while in-app template features use the same table; (3) the `api_clients`/`api_access_tokens`/`api_request_logs` tables (created in supabase/migrations/20260110172925_a9616e50-9aa9-4128-8fa1-4e8852cde733.sql:2,16,29 — unit D02) shared with the admin APIClients view; (4) human-readable endpoint documentation — src/views/APIClients.tsx (V02) renders curl-style samples for oauth-token (:411,467) and api-reports (:435,451) inside JSX template strings.

## supabase/functions/templates/index.ts

- Purpose: Serves the DocBuilder integration a catalogue of six hard-coded report-template structures plus a seventh inline inspection-report entry, each populated with `availableItems` drawn from live table reads, alongside all stored `inspection_templates` rows and a data summary.

Requires header `Authorization: Bearer <DOCBUILDER_PUBLIC_TOKEN>` (:344-374). Success response (:515-537): `{ success: true, app: 'wm-compliance', summary: {totalClients, totalSites, totalSubsections, totalInspections, totalFloorPlans, totalCocValidations, totalTemplates, totalSnags, totalAssets}, reportTypes: [...], inspectionTemplates: [...], clients: [] }`. Module-private const `reportTemplateStructures` (:9-336) defines site-summary, subsection-report, floor-plan-report, coc-validation-report, defect-report, asset-verification-report; each emitted reportType gains `requiredParams` (:448-451) and `availableItems` (:406-454); an `inspection-report` entry is pushed inline (:457-501).
- Inputs & outputs: In — Authorization header only. Env — `DOCBUILDER_PUBLIC_TOKEN` (:345), `SUPABASE_URL` (:376), `SUPABASE_SERVICE_ROLE_KEY` (:377). Tables read in parallel (:383-399): `sites`, `subsections`, `inspections`, `subsection_floor_plans`, `inspection_templates`, `snags`, `site_assets`, each with an explicit column list. `clients` is deliberately not queried (comments :381-382, :532-534; `totalClients: 0` at :504). Out — the JSON catalogue above. No storage buckets, no browser storage.
- Dependencies: uses -> `createClient` from `https://esm.sh/@supabase/supabase-js@2` (:1); no repo-internal imports. used by <- none found (grep-verified: `grep -rn "invoke('templates'\|invoke(\"templates\"\|functions/v1/templates" src supabase` → no hits).
- Side effects: seven parallel read-only DB queries (:391-399); no writes, no outbound calls, no events.
- Error handling: `DOCBUILDER_PUBLIC_TOKEN` unset → 503 `{error: 'DOCBUILDER_PUBLIC_TOKEN is not configured'}` (:348-353). Token mismatch → 401 `{error: 'Invalid API key'}` after constant-time SHA-256 digest XOR comparison (:355-374). Any throw → `console.error` + 500 `{error: message}` (:538-545). The seven queries destructure only `{ data }` (:383-390); a per-query error is never inspected — downstream `?.` / `|| []` fallbacks (:402-403, :412-441, :496-512, :521-531) yield empty maps/arrays/zero counts.

(3) coc-validation-report declares `requiredParams: ['validationId']` (:451) while its `availableItems` are subsection ids filtered on `coc_status` (:431-434), with the comment ":430" stating COC is now a manual per-subsection verdict with no validation records. ## supabase/functions/save-template/index.ts

- Purpose: Accepts a DocBuilder-format template plus an action string and creates, updates, or (per the code's intent) deletes the corresponding `inspection_templates` row.
- Public surface: HTTP only. `Deno.serve(async (req) => Response)` at :8. POST JSON `{ template, action }` (:25) where action is `'create' | 'update' | 'delete'`. Optional `Authorization: Bearer <DOCBUILDER_PUBLIC_TOKEN>` (:15-23). Success response `{ success: true, templateId, action: 'created'|'updated'|'deleted' }` (:65,78,89,99-102).
- Inputs & outputs: In — JSON body; template fields mapped to DB columns at :42-52 (`name`, `category` default `'General'`, `description`, `sections` default `[]`, `cover_page` from `coverPage`/`cover_page`, `tenants`, `sections_count` from `sections.length`, `pages_count` from `pagesCount`/`pages_count`, `updated_at` = now — set on insert as well as update). Env — `DOCBUILDER_PUBLIC_TOKEN` (:16), `SUPABASE_URL` (:35), `SUPABASE_SERVICE_ROLE_KEY` (:36). Tables — `inspection_templates` insert (:58-62), update (:70-75), delete (:83-86). Out — the result JSON.
- Dependencies: uses -> `createClient` from `https://esm.sh/@supabase/supabase-js@2` (:1). used by <- none found (grep-verified: `grep -rn "save-template" src supabase` → only self-references).
- Side effects: one `inspection_templates` mutation per call; `console.log` on receipt (:39) and per outcome (:66,79,90); no outbound calls.
- Error handling: missing `template` → 400 (:27-32). Auth: **fail-open** — the key is checked only `if (expectedApiKey && ...)` (:18), so an unset env var admits every caller; when set, comparison is a plain string equality on the whole header (:18), not the digest compare used in templates/index.ts:355-374. Unrecognised action/id combination → 400 `{error: 'Invalid action or missing template ID'}` (:92-97). Any supabase error is `throw`n (:64,77,88) into the catch → `console.error` + 500 `{error: message}` (:104-111).
- Tests: none found (see unit header).
- Observed issues: (1) The delete branch is unreachable when `template.id` is present: branch order is `action === 'create' || (!template.id && action !== 'delete')` (:56), then `action === 'update' || template.id` (:68), then `action === 'delete' && template.id` (:81). A request with `action: 'delete'` and a `template.id` satisfies `template.id` at :68 and performs an UPDATE; with `action: 'delete'` and no id, all three branches fail and the caller gets the 400 at :92-97. No input reaches :81-90. (2) Fail-open auth contrasted with the fail-closed sibling using the same env var (templates/index.ts:348-353). (3) `updated_at` is written on create as well (:51 inside the shared `dbTemplate`).
- ASSUMED: caller is DocBuilder (comment :14 "Validate API key from DocBuilder (optional)"); the create/update/delete `action` vocabulary is DocBuilder's, not defined anywhere in this repo.

## supabase/functions/oauth-token/index.ts

- Purpose: OAuth2-style token endpoint that exchanges client credentials or a refresh token for a new access/refresh token pair stored in `api_access_tokens`.
- Public surface: HTTP only. `serve(async (req) => Response)` at :10, methods POST/OPTIONS (:7). POST JSON `{ grant_type, client_id, client_secret, refresh_token }` (:20); `grant_type` must be `client_credentials` or `refresh_token` (:23). Success 200 (:104-113): `{ access_token, token_type: "Bearer", expires_in: 3600, refresh_token, scope: clientRecord.scopes.join(" ") }`.
- Inputs & outputs: In — the JSON grant request. Env — `SUPABASE_URL` (:16), `SUPABASE_SERVICE_ROLE_KEY` (:17). Tables — `api_clients` select by `client_id` + `client_secret` + `is_active` (:34-40); `api_access_tokens` select joined `api_clients(*)` by `refresh_token` with `refresh_expires_at` filter (:51-56), delete of the rotated token row (:66), insert of the new token row `{client_id, access_token, refresh_token, scopes, expires_at, refresh_expires_at}` (:76-83); `api_request_logs` insert on success (:94-102). Out — the token JSON. Token values are two concatenated `crypto.randomUUID()` results, the second with dashes stripped (:71-72); access TTL 1 hour, refresh TTL 30 days (:73-74).
- Dependencies: uses -> `serve` std@0.168.0 (:1), `createClient` esm.sh supabase-js@2 (:2). used by <- src/views/APIClients.tsx:411,467 (V02) — documentation strings in the admin UI; supabase/functions/api-reports/index.ts:112 names `/oauth-token` in its /available response (intra-unit reference). No programmatic in-repo caller (grep-verified).
- Side effects: inserts a token row per successful grant (:76-83); deletes the old token row on refresh (:66); inserts an `api_request_logs` row with `status_code: 200` after success (:94-102); `console.error` on insert failure (:86).
- Error handling: unsupported grant_type → 400 `{error:'unsupported_grant_type'}` (:24-27); bad client credentials → 401 `{error:'invalid_client'}` (:42-47); invalid/expired refresh token or inactive client → 401 `{error:'invalid_grant'}` (:58-63); token insert failure → 500 `{error:'server_error', error_description:'Failed to generate token'}` (:85-91); catch-all → 500 with `error.message` (:114-121). Errors from the delete at :66 and the request-log insert at :94-102 are not inspected.
- Tests: none found (see unit header).
- Observed issues: (1) `client_secret` is matched by a plaintext DB equality query (:37-38), i.e. secrets are stored and compared in plaintext; issued access and refresh tokens are likewise stored as plaintext columns (:76-83) — api-reports looks tokens up by plaintext equality too (api-reports/index.ts:21-22). (2) On refresh, the old token row is deleted before the new insert is attempted (:66,76); an insert failure (:85-91) leaves the client with neither token. (3) `scope: clientRecord.scopes.join(" ")` (:110) calls `.join` without a null guard. (4) The success log row is the only logging path — failed grants produce no `api_request_logs` row (:94-102 sits after all failure returns).
- ASSUMED: token randomness relies on `crypto.randomUUID()` (UUIDv4); no other entropy source is used — stated as read, no claim about sufficiency.
