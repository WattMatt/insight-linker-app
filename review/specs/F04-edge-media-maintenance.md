## Unit header

**Unit purpose.** Four self-contained Deno edge functions for storage-image maintenance: single-image server-side compression (compress-image), bulk bucket compression with dry-run (batch-compress-images), and two one-off data-repair jobs that rewrite broken photo URLs stored inside `inspections.json_data` (fix-inspection-photos, fix-tenant-images). Compression is delegated to Supabase's image-transformation service via signed URLs; the repair jobs fuzzy-match replacement files in storage folders.

**Module-level observations (cross-file, all verified in-file).**
- No file contains an `export` statement; the entire surface of each is one HTTP handler registered via `Deno.serve` (compress-image/index.ts:47, batch-compress-images/index.ts:93, fix-inspection-photos/index.ts:196, fix-tenant-images/index.ts:25).
- All four import exactly one dependency: `createClient` from `https://esm.sh/@supabase/supabase-js@2` (line 1 of each file), and all four build their client from `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` (compress-image:72-74, batch-compress-images:116-118, fix-inspection-photos:9-13 + 202-203, fix-tenant-images:31-33).
- All four declare the same `corsHeaders` const with `Access-Control-Allow-Origin: '*'` and answer OPTIONS preflight with it (compress-image:3-6/48-50, batch-compress-images:3-6/94-96, fix-inspection-photos:3-6/197-199, fix-tenant-images:3-6/26-28).
- `detectImageType(bytes)` is duplicated verbatim between the two compression functions (compress-image:25-31, batch-compress-images:38-44); the G-SEC-12 in-file auth block is likewise near-identical between them (compress-image:76-87, batch-compress-images:120-131). The two fix-* functions have no in-file auth block at all.
- Auth split per supabase/config.toml: `compress-image` verify_jwt=true (config.toml:52-53), `batch-compress-images` verify_jwt=true (config.toml:55-56), `fix-tenant-images` verify_jwt=true (config.toml:36-37), `fix-inspection-photos` verify_jwt=false (config.toml:49-50).
- No test file anywhere covers this unit: `git ls-files '*test*' '*spec*' | grep -i "compress\|imageupload\|ImageCompression"` → no matches; there are no test files under supabase/functions.
- Nothing in the app reads the compressed outputs back: `grep -rn "_compressed" src` matches only the status-enum strings in src/components/settings/ImageCompressionManager.tsx:17,91,232 — no src code constructs or fetches `*_compressed.*` storage paths.

**External contract.** The app invokes two of the four functions: H02's `src/hooks/useImageUpload.ts:241` fire-and-forgets `compress-image` after every upload to the `inspection-photos` bucket (guard at useImageUpload.ts:193-195), and C05's `src/components/settings/ImageCompressionManager.tsx:48` invokes `batch-compress-images` from an admin settings panel. The two fix-* repair functions have zero in-repo callers (grep-verified) and exist only as HTTP endpoints; docs/system-reference/GAPS.md:36 states both were deleted from production with source kept in repo (docs claim, not verifiable from this repo). The functions' `verify_jwt` registry lives in D04 (supabase/config.toml).

## supabase/functions/compress-image/index.ts

- Purpose: Compresses one stored image via a Supabase image-transformation signed URL and uploads the result (or, failing that, the original bytes) as a `_compressed` sibling object.
- Public surface: HTTP only — `Deno.serve(async (req) => Response)` (line 47); no module exports. Request: POST JSON `CompressImageRequest { sourcePath: string; bucket?: string; maxWidth?: number; quality?: number }` (8-13), defaults `'inspection-photos'`/800/70 (54-59). Response: `CompressImageResponse { success: boolean; originalSize?: number; compressedSize?: number; path?: string; url?: string; error?: string }` (15-22). Module-private: `detectImageType(bytes: Uint8Array): string` (25-31), `arrayBufferToBase64(buffer: ArrayBuffer): string` (34-45).
- Inputs & outputs: env `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (72-73). Storage (bucket from body, default `inspection-photos`): download `sourcePath` (90-92); createSignedUrl 60s with `transform: { width, quality }` (112-119); upload `<pathWithoutExt>_compressed.<ext>` with `upsert: true` (150-159); getPublicUrl of the compressed path (170-172). No tables. Auth: verify_jwt=true (supabase/config.toml:52-53) plus in-file G-SEC-12 check — JWT from the Authorization header must resolve to a real user via `supabase.auth.getUser(jwt)` (76-87).
- Dependencies: uses -> `createClient` from `esm.sh/@supabase/supabase-js@2` (line 1); no repo imports. used by <- H02 offline-domain-hooks (src/hooks/useImageUpload.ts:241, `supabase.functions.invoke('compress-image', ...)` inside `triggerServerCompression`, fire-and-forget, only when bucket is `inspection-photos` and `options?.skipServerCompression` is falsy, useImageUpload.ts:193-195); config entry in D04 db-platform-config (supabase/config.toml:52-53). Grep basis: `grep -rn "compress-image" src supabase`.
- Side effects: storage upload (154-159); outbound fetch of the signed transform URL with a 30s AbortSignal timeout (123-125); console.log/warn/error throughout (68-69, 95, 103, 131, 134, 140, 162, 174-175, 191).
- Error handling: missing `sourcePath` → 400 JSON (61-66); failed auth → 401 `{ error: 'Unauthorized' }` (83-87); download failure → 404 with `Download failed: <msg>` (94-100); transform-fetch throw → console.warn, keep original bytes, continue (133-135); non-OK transform response → silently keep original (127-132); upload failure → 500 `Upload failed: <msg>` (161-167); any other throw (including JSON body parse) → top-level catch, 500 `{ success: false, error }` (190-196). The body is parsed at line 53, before the auth check at 79-87, so a malformed body from an unauthenticated caller returns 500 via the catch rather than 401.
- Tests: none found (grep-verified as per unit header).
- Observed issues:
  - `arrayBufferToBase64` (34-45) is defined and never called in the file.
  - When transformation is unavailable, the function uploads the original bytes unchanged under the `_compressed.<ext>` name — `compressedData` is initialised to the original buffer (107-108) and the upload at 154-159 runs unconditionally, with no size-reduction guard (contrast batch-compress-images:260).
  - `detectImageType` reads only the first two bytes; `0x52 0x49` ("RI" of RIFF) is mapped to `image/webp` (29), which also matches non-webp RIFF containers.
  - GIF-detected bytes get contentType `image/gif` (28) but the extension mapping has no gif branch, so `newExt` falls through to `'jpg'` (145-147).
  - The only consumer discards the response: useImageUpload.ts:248-252 has an empty block on `data?.success`, and no src code reads `_compressed` paths (grep-verified).
- ASSUMED: the transformation path only works on a Supabase Pro plan (in-file comment at line 105); actual plan status and hence which branch runs in production is not verifiable from the repo.

## supabase/functions/batch-compress-images/index.ts

- Purpose: Scans a storage bucket (BFS over folders) and bulk-creates `_compressed.jpg` siblings for images above a size threshold, with a dry-run mode and per-file result reporting.
- Public surface: HTTP only — `Deno.serve` (93); no exports. Request: POST JSON `BatchCompressRequest { bucket?: string; prefix?: string; maxWidth?: number; quality?: number; minSizeKB?: number; dryRun?: boolean; limit?: number }` (8-16), defaults `'inspection-photos'`/''/800/70/150/false/50 (100-108). Response: `BatchCompressResponse { success, processed, compressed, skipped, errors, totalSavings, files: ProcessedFile[], continuationToken? }` (26-35) with `ProcessedFile { path, originalSize, compressedSize?, status: 'compressed'|'skipped'|'error'|'already_compressed', error? }` (18-24). Module-private: `detectImageType(bytes)` (38-44); `listFilesFlat(supabase, bucket, prefix = '', maxDepth = 4): Promise<Array<{name, path, size?}>>` (48-91), invoked with maxDepth 5 (135), BFS capped at MAX_FOLDERS=100 (57) and 500 items per list call (65).
- Inputs & outputs: env `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (116-117). Storage (bucket from body): list (63-65); per-candidate download (165-167); probe-download of the `_compressed.jpg` sibling (196-199); createSignedUrl 120s with transform (224-231); upload `_compressed.jpg` upsert (274-279). No tables. Candidate filter (139-147): extension in jpg/jpeg/png/webp/heic, name/path not containing `_compressed`, and `!file.size || size >= minSizeKB`. Auth: verify_jwt=true (supabase/config.toml:55-56) plus the same in-file G-SEC-12 getUser check (120-131).
- Dependencies: uses -> `createClient` from `esm.sh/@supabase/supabase-js@2` (line 1); no repo imports. used by <- C05 settings-panels (src/components/settings/ImageCompressionManager.tsx:48, `supabase.functions.invoke('batch-compress-images', ...)` passing bucket/maxWidth/quality/minSizeKB/dryRun/limit from panel state, ImageCompressionManager.tsx:49-56); config entry in D04 (supabase/config.toml:55-56). Grep basis: `grep -rn "batch-compress-images" src supabase`.
- Side effects: storage uploads (274-279); outbound fetch of signed transform URLs, 30s timeout (238-240); extensive console logging (89, 110-113, 134-136, 149, 191, 208, 219, 250, 268, 303, 327-328, 336).
- Error handling: auth fail → 401 (127-131); folder-list error → console.error and skip that folder, scan continues (67-70); per-file download error → `status: 'error'` entry, `errors++`, continue (169-178); transform fetch throw or non-OK → fallback to original bytes (245-253, and 254-257 when signed-URL creation itself fails); upload error → per-file `'error'` entry (281-290); any per-file throw → caught, `'error'` entry (305-313); top-level throw (including body parse) → 500 `{ success: false, error }` (335-341). The 200 response always has `success: true` regardless of the per-file `errors` count (316-317).
- Tests: none found.
- Observed issues:
  - `continuationToken` is emitted as the literal string `` `offset_${limit}` `` when more candidates exist (324), but `BatchCompressRequest` (8-16) has no field that accepts a continuation token or offset, so it cannot be fed back into a subsequent call.
  - In dry-run mode, files that "would be compressed" are pushed with `status: 'skipped'` but the `skipped` counter is not incremented (212-221; counter increments only at 190, 207, 267), so the summary counters and the per-file statuses disagree on dry runs.
  - `compressedPath` hardcodes the `.jpg` extension (196) while the upload contentType is taken from magic bytes (273) — a transform that returns webp/png bytes is stored as `*.jpg` with a non-JPEG content type.
  - When transformation is unavailable, the fallback bytes are byte-identical to the original, so the `compressedSize >= originalSize * 0.9` guard (260-270) always records `'skipped'` — this function never uploads uncompressed originals, unlike compress-image.
  - Existence check for a prior compressed sibling downloads the entire object rather than statting it (197-199).
  - `listFilesFlat` classifies any item without `item.metadata?.size` as a folder and enqueues it for scanning (76-85), so metadata-less or zero-size files are treated as folders.
- ASSUMED: that Supabase `storage.list()` reliably returns `metadata.size` for files and no metadata for folders (the classification at 76-82 depends on it) — platform behavior, not verifiable in-repo.

## supabase/functions/fix-inspection-photos/index.ts

- Purpose: One-off repair job that scans inspections' `json_data`, tests every stored public photo URL for existence, and rewrites broken ones to a fuzzy-matched file in the same storage folder, persisting the modified `json_data`.
- Public surface: HTTP only — `Deno.serve` (196); no exports; no method filter beyond OPTIONS. Request: JSON body, optional (parse failure defaults to `{}`, line 205): `{ inspectionId?: string; dryRun?: boolean }` (206-207). Response: `{ success: true, dryRun, summary: { inspectionsProcessed, inspectionsWithIssues, totalFixed, totalNotFound }, results: Array<{ inspectionId, title, siteId, subsectionId, fixed, notFound, changes: string[] }> }` (272-285), or `{ success: true, message: 'No inspections found', results: [] }` (227-232). Module-private: `getSupabaseClient()` (9-13); `parseStorageUrl(url): { bucket, path } | null` (16-35, only `/storage/v1/object/public/` URLs); `buildStorageUrl(baseUrl, bucket, path)` (38-40); `fileExists(supabase, bucket, path)` (43-46); `findMatchingFile(supabase, bucket, originalPath): Promise<string | null>` (49-101) — strategy 1: itemId+index match, strategy 2: itemId match, strategy 3: first image file in the directory, with a hardcoded itemId vocabulary (`boardOpen`, `boardClosed`, `internalLegend`, `mainBreaker`, `meter`, `ct`, `earthLeakage`, `other`, `cleanliness`, `mainCableGland`, `generalWiring`, 63-67); `processInspectionPhotos(supabase, baseUrl, inspectionId, jsonData): Promise<{ fixed, notFound, changes }>` (104-194).
- Inputs & outputs: env `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (10-11, 203). Table `inspections`: select `id, title, json_data, site_id, subsection_id` where `json_data` not null, optional `.eq('id', inspectionId)`, `.limit(100)` (212-221); update `{ json_data, updated_at }` (183-186). Storage: whatever bucket appears in stored URLs — download to test existence (44), list directory with limit 100 (74). json_data locations walked: `normalBoardImages`, `emergencyBoardImages`, `componentImages`, `normalWiringImages`, `emergencyWiringImages` → `<section>.<itemId>.photos[]` (140-163), plus `tenants[].meterImage/breakerImage/ctRatioImage` (166-179). Auth: verify_jwt=false (supabase/config.toml:49-50) and no in-file auth check of any kind — anonymous callers reach the mutation path.
- Dependencies: uses -> `createClient` from `esm.sh/@supabase/supabase-js@2` (line 1); no repo imports. used by <- none found (grep-verified: `grep -rn "fix-inspection-photos" src supabase` hits only supabase/config.toml:49; doc mentions exist in docs/APPLICATION_SPEC.md:1461, docs/security/2026-06-09-auth-access-security-audit.md:75, docs/system-reference/{GAPS.md:32,36; SECURITY-FINDINGS-phase2.md:23; 05-edge-functions/images-maintenance.md}).
- Side effects: DB updates of `inspections.json_data` + `updated_at` (183-186); storage downloads/lists per URL checked (44, 74); console logging (209, 234, 243, 270, 287).
- Error handling: body parse failure → silently defaults to `{}` (205); inspections fetch error → `throw` → top-level catch → 500 `{ success: false, error }` (223-224, 286-295); per-inspection update error → appended to `changes` as an `ERROR updating inspection: <msg>` string, not surfaced as a failure and not decremented from `fixed` (188-190); there is no per-URL try/catch, so an exception thrown inside `fileExists`/`findMatchingFile` aborts the whole run via the top-level catch.
- Tests: none found.
- Observed issues:
  - `dryRun` does not suppress the database write. The handler passes a deep copy (`jsonDataCopy`, 246) when `dryRun` is true and the live object otherwise (248-253), but `processInspectionPhotos` takes no dryRun parameter and unconditionally runs the `inspections` update whenever `modified` is true (182-191) — so both branches persist rewritten `json_data` for the same `inspection.id`; the flag only changes which in-memory object is mutated, plus the echoed `dryRun` field in the response (275).
  - Anonymous and mutating: verify_jwt=false with no in-handler check while updating `inspections.json_data` via the service-role client; the sibling repair function fix-tenant-images is verify_jwt=true (config.toml:36-37 vs 49-50).
  - Match strategy 3 rewrites a missing photo URL to the alphabetically-first image file in the directory with no name-similarity requirement (96-100).
  - `fileExists` downloads the entire object to test existence (44).
  - The `.limit(100)` cap (221) applies to the scan-all path with no continuation mechanism; the response does not indicate whether more than 100 inspections exist.
  - docs/system-reference/GAPS.md:36 states this function was deleted from production ("0 callers, verified 404; source kept in repo") — a docs claim about the live project.
- ASSUMED: the docs' prod-deletion claim (GAPS.md:36) cannot be verified from the repo; the one-off-maintenance intent is inferred from the function name and docs, not from any in-code guard.

## supabase/functions/fix-tenant-images/index.ts

- Purpose: One-shot repair that scans every inspection whose `json_data->tenants` is non-null and rewrites each broken tenant image URL (`breakerImage`, `ctRatioImage`, `meterImage`) to the most recent image in the same `inspection-photos` folder.
- Public surface: HTTP only — `Deno.serve` (25); no exports; accepts any method (only OPTIONS special-cased, 26-28) and never reads a request body. Response: `{ success: true, summary: { totalProcessed, fixed, notFound, alreadyValid }, details: FixResult[] }` (164-179). Module-private interfaces: `Tenant { id: string; breakerImage?; ctRatioImage?; meterImage?; [key: string]: unknown }` (8-14); `FixResult { inspectionId, tenantId, field, originalUrl, fixedUrl: string | null, status: 'fixed' | 'not_found' | 'already_valid' }` (16-23).
- Inputs & outputs: env `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (31-32). Table `inspections`: select `id, json_data` where `json_data->tenants` not null, with NO limit (41-44); update `{ json_data }` per modified inspection (151-154). Storage `inspection-photos`: list folder with limit 50 sorted `created_at` desc (81-83); getPublicUrl of the replacement (109-111). URL path extraction via regex `/inspection-photos\/(.+?)(?:\?|$)/` + decodeURIComponent (70-73). Auth: verify_jwt=true (supabase/config.toml:36-37); no in-file check — any holder of a platform-accepted JWT triggers the full scan.
- Dependencies: uses -> `createClient` from `esm.sh/@supabase/supabase-js@2` (line 1); no repo imports. used by <- none found (grep-verified: `grep -rn "fix-tenant-images" src supabase` hits only supabase/config.toml:36; doc mentions in docs/APPLICATION_SPEC.md:1460, docs/security/2026-06-09-auth-access-security-audit.md:109, docs/system-reference/{GAPS.md:32,36; SECURITY-FINDINGS-phase2.md:24; 05-edge-functions/images-maintenance.md}).
- Side effects: DB updates of `inspections.json_data` (151-154); storage list calls per image field (81-83); console logging (50, 86, 129, 157, 159, 183).
- Error handling: inspections fetch error → `throw` → top-level catch → 500 `{ success: false, error }` (46-48, 181-191); per-folder list error → console.error and skip that field, scan continues (85-88); non-matching URL (regex miss) or missing filename/folder → field silently skipped (71, 78); per-inspection update error → console.error only — the run continues and the response still reports those fields as `'fixed'` (156-160); exact filename found → `'already_valid'`, no change (91-103); no image file in folder → `'not_found'` (130-140).
- Tests: none found.
- Observed issues:
  - No `dryRun`, no `limit`, no request parameters at all — every invocation is a live, unbounded rewrite pass over all tenant-bearing inspections (41-44).
  - Replacement selection is "first image in the created_at-descending listing" (81-83, 106) regardless of filename similarity, so a tenant field can be re-pointed at an unrelated image.
  - When the final `inspections` update fails, the corresponding `FixResult` entries keep `status: 'fixed'` and `fixedCount` is not decremented (113-129 vs 151-158) — the summary can report fixes that were never persisted.
  - `summary.totalProcessed` is `results.length`, i.e. a count of tenant image *fields* evaluated, not inspections (168).
  - The update writes only `json_data` and does not touch `updated_at` (151-154), unlike fix-inspection-photos (fix-inspection-photos/index.ts:185).
  - docs/system-reference/GAPS.md:36 lists this function among those deleted from production with source retained — a docs claim about the live project.
- ASSUMED: the docs' prod-deletion claim is unverifiable from the repo; folder listing sorted by `created_at desc` returning the "most recent" file first relies on Supabase storage list semantics.
