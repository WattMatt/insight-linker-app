# Pre-Mortem — Security Remediation Plan

**Plan:** Lock down the confirmed anonymous-access exposures (audit: `2026-06-09-auth-access-security-audit.md`) via a tiered SQL migration, then rebuild the public portal and complete Tier 3.
**Pre-mortem date:** 2026-06-09
**Prospective horizon:** 3 months (acute) + 12 months (tail)
**Failure frame:** *"It is September 2026. The remediation failed — the app was breached anyway, and/or the lockdown broke production, and/or it half-happened and the worst hole is still open. Looking back, what went wrong?"*

---

## Plan summary (baseline)
- **Objective:** No unauthenticated party can read the dataset, harvest share tokens, or read/write/delete files; logged-in app keeps working; sharing rebuilt securely.
- **Milestones:** Tier 1+2 migration (now) → verify → rotate leaked password → Tier 3 (storage, portal rebuild, edge-function auth, self-signup, RLS sweep).
- **Critical assumptions:** (a) migration covers all exposed tables; (b) only 1 share link, so breakage is tiny; (c) applying via SQL editor is safe; (d) locking down now resolves the exposure.
- **Key dependencies:** Supabase live DB matches migrations; Lovable doesn't re-introduce policies; one operator (Arno) follows through; field devices/offline-sync tolerate tighter RLS.

---

## TOP 5 FAILURE MODES (probability × impact)

### #1 — Tier 3 is abandoned; the *worst* hole (anon can DELETE every file) stays open — CRITICAL
**Probability:** HIGH · **Impact:** CRITICAL
**Root cause (5 Whys):** The acute pain (anon *read*) is relieved by Tier 1+2 → urgency evaporates → Tier 3 slips → the catastrophic storage policy (`Anyone can delete from all storage`, anon) and the unauthenticated service-role edge functions remain indefinitely. The deepest cause: we sequenced the *most visible* fix first, not the *most dangerous* one.
**Early warning:** Tier 3 has no owner/date; "we'll get to storage later" appears in notes; 2+ weeks pass with Tier 3 untouched.
**Prevention:** **Pull the zero-breakage storage write/update/delete lockdown into the NOW migration** (anon has no legitimate reason to write/delete files). Give Tier 3 explicit dates. → *Acted on this turn: storage write/delete added to the revised migration.*

### #2 — The migration leaves tables open but reports success (false "fixed") — HIGH
**Probability:** HIGH (in the original) · **Impact:** HIGH
**Root cause:** Hardcoded 12-table list instead of scanning the schema. PROVEN by probe: `coc_extractions`, `site_assets`, `schematic_blocks`, `site_schematics` (465 rows) were exposed and **not** in the list.
**Early warning:** Post-apply probe of only the "fixed" tables returns 0 (looks done) while un-probed tables stay open.
**Prevention:** (a) Migration now **scans all `public` tables** for anon/public `USING(true)` SELECT and demotes them — no hardcoded list. (b) Verification re-probes **all 48 tables**, not the 12. → *Acted on this turn.*

### #3 — Lovable silently re-opens the holes on the next AI edit — HIGH
**Probability:** HIGH over 12 months · **Impact:** HIGH
**Root cause:** The insecure `USING(true)`/`TO anon` policies were generated by Lovable's AI to "make the public page work." Ask Lovable to touch the portal/QR/public pages again and it may regenerate them — silently undoing the fix.
**Early warning:** Any Lovable change touching public pages, RLS, or "sharing"; a new migration appears with `USING (true)`.
**Prevention:** Save the anon-probe script as a **regression check** and re-run it after *every* Lovable change. When prompting Lovable near these features, explicitly forbid `USING(true)`/anon SELECT. Keep a CI/manual checklist.

### #4 — The data was already scraped during the months-long exposure (POPIA) — HIGH
**Probability:** MEDIUM (unknown, untestable after the fact) · **Impact:** HIGH
**Root cause:** These anon policies have been live since ~Jan 2026. Locking down now stops *future* access but does nothing about exfiltration that already happened — and there is **no detection** in place. Under POPIA, a breach of client PII may trigger notification duties.
**Early warning:** Unusual anon request volume in Supabase API logs; client PII appearing elsewhere.
**Prevention:** Check Supabase **API/edge logs** for anonymous `/rest/v1/*` read volume on `clients`, `inspections`, etc. Assess POPIA notification with the client/legal. Decide whether disclosure is required. *Cannot be undone by the migration — needs a human decision.*

### #5 — Breakage is bigger than "1 share link": field QR codes die — MEDIUM-HIGH
**Probability:** MEDIUM-HIGH · **Impact:** MEDIUM-HIGH
**Root cause:** I equated "anon surface" with "the 1 `client_access_links` row." But `PublicSubsection` (`/public/subsections/:id`) is a **token-less QR landing page** reading tables directly as anon. If inspectors/clients scan QR codes on-site, Tier 2 breaks **all of them**, not one link.
**Early warning:** QR codes in the field return blank/errors; client/inspector complaints right after apply.
**Prevention:** **Confirm QR usage before applying.** If QR is live, either rebuild that read behind a token RPC first, or accept + communicate the outage. (Authenticated app is unaffected.)

## What this plan does well (balanced view)
- It **verified before changing** (live probe), which is exactly what caught the coverage gap.
- It is **tiered by blast radius**, so the zero-breakage closures can ship immediately.
- The fix is **idempotent and reversible-shaped**, and tracked as a migration.
- It correctly identified that the public portal is the architectural root cause (not a code bug) and routed the real fix to a proper rebuild rather than another `USING(true)` patch.
- The biggest residual risks are organizational (follow-through), not technical — and those are now named, owned, and dated.
