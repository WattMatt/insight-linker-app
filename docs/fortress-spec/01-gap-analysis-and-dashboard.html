Fortress Building Dashboard — gap analysis & build plan

Reviewing the existing spec set against the three “Fortress specs” (the Abaqulusi Plaza property-report pack), mapping the gap to what Insight Linker builds today, and proposing a per-building dashboard driven by the Fortress report structure — with every KPI linked to a data source, an app module, and a build status, so it can be added to the application.

One-line task restatement: analyse the 3 Fortress report workbooks vs the current build, produce a gap-based plan, and design a full per-building dashboard with detailed KPIs each clearly linked to the relevant parts of the app — as an addition to Insight Linker.  Status: plan only — nothing built or run yet.

What the “Fortress specs” actually are

Three Excel workbooks for Abaqulusi Plaza (Vryheid), a Fortress / Capital Propfund shopping centre managed under Broll:

Naming clash to resolve. The app already contains a template called FORTRESS - Complete Compliance Inspection (src/lib/fortressTemplate.ts) — but that is WM’s electrical scope-of-works (RMUs, mini-subs, DBs). The new “Fortress specs” are the client’s property-management report pack, which is far broader. This plan treats them as two different things and proposes calling the new module the Fortress Building Report Pack / Dashboard.

1 · Gap analysis — Fortress specs vs current build

Insight Linker today is an electrical-compliance system: Client → Site → Subsection (board) → Inspection, plus COC, snags, metering, an operational Site-Health score, PDF reports, photos and offline capture. The Fortress pack demands a whole property/facilities-management layer on top of that electrical core.

Shape of the gap. The app already nails the electrical safety spine (domains 1–4) and has a reusable inspection + snag + PDF engine. The Fortress pack reframes that spine as one section of a much larger building operations record. The biggest net-new pieces are an asset register (10) and the schedules/ledgers hanging off it — PPM (11), utilities (12), OHS scoring (9). The commercial domains (14–15, trading & leasing) are property-manager data WM may display/import rather than capture.

Scope boundary worth confirming

WM Consulting Electrical Engineers’ natural mandate is the engineering/compliance + condition half of the pack (domains 1–13, 16–17). The commercial half (trading, leasing, arrears, footfall, toilet fund) is the centre manager’s data. The dashboard is designed so commercial KPIs are optional import-only tiles — present for a complete building picture, but not blocking the engineering build. See Decision D5.

The single-source-of-truth principle (carry over from Site-Health redesign)

The Site-Health redesign already established the rule: one pure module owns each score, screen + PDF both call it. Extend that — add buildingCompliance.ts (OHS %), ppm.ts (schedule rollups) and utilities.ts (yields/variance) as pure, unit-tested functions next to siteHealth.ts. The dashboard cards, the report generator, and any RLS-safe RPC all read the same functions — no divergent calculators (the exact bug class the redesign was fixing).

5 · Phased build plan

Sequenced so each phase ships a usable slice and de-risks the next. Effort is rough order-of-magnitude (S ≈ days, M ≈ 1–2 wks, L ≈ 3–4 wks) for one engineer, assuming the Site-Health redesign lands first.

P0Foundations & auditS–M
  • Read-only audit of live sites/subsections/snags/document_categories schemas; reconcile with system-reference docs.
  • Land the in-flight Site-Health redesign (single SoT, snag-status migration) — the dashboard depends on it.
  • Extend sites with building-profile fields; build the building identity header.
  • Decide buildings-as-sites vs new entity (Decision D1) and naming vs the existing electrical “FORTRESS” template (D6).
P1Asset register + PPM (the spine)L
  • building_assets + ppm_tasks tables, RLS, CRUD UI, and an Excel importer seeded from the Annual report layout.
  • ppm.ts pure rollups → Group C cards (due/overdue/on-schedule).
  • Asset-driven service reminders via existing calendar_events / notifications.
  • Why first: it’s the largest net-new domain and most other groups reference assets.
P2Condition inspection + OHS complianceM–L
  • Add condition + action_timeframe to inspection_items; seed Building-Condition + OPS-monthly templates.
  • ohs_compliance_items + buildingCompliance.ts weighted % → hero card + Group A.
  • Wire Group B condition KPIs to the new fields; reuse snag pipeline for action items.
P3Utilities + tenants/shop-specL
  • utilities_readings + utilities.ts (solar/borehole yield, water balance, night usage) → Group D.
  • First-class tenants + tenant_shop_specs; migrate subsections.tenant_name into it.
  • Tenant compliance matrix (evac/HVAC/COC/flammable) → Group E; Excel import from CM OHS & HK / Shop Spec.
P4Ledgers + report pack generationM
  • Thin tables: masterfile_index, expense_recoveries, security_incidents → Groups G/H.
  • Generate the OPS, CM and Annual PDF/Excel packs from captured data, reusing the pdfmake/PdfShift pipeline and the shared KPI functions.
  • Commercial tiles (Group F) as import-only from CM Page 2 (Decision D5).
P5Multi-building portfolio & polishM
  • Portfolio roll-up across buildings (compliance %, overdue services, incidents) for asset managers.
  • Offline capture parity for asset/PPM/condition; photo evidence per asset (reuse offline_photos).
  • Unit tests on every pure KPI module; visual parity check screen ↔ PDF.
De-risking order: P0 unblocks everything; P1 builds the spine the rest reference; P2 reuses the most existing engine for fast visible value; P3–P4 are mostly data-entry + import + a report generator over a stable model.

6 · Decisions & open questions

ADR-style log. All entries are PROPOSED until confirmed — none should be treated as locked. History stays visible; a reversal is a new dated entry, never an edit in place.

D1 — Buildings modelled on existing sites PROPOSED

Add a building-profile extension rather than a new entity. Reuses all RLS, portals, inspections, COC and PDF wiring. Reversible to a dedicated buildings table if multi-site-per-building emerges.

D2 — building_assets is the spine of the property layer PROPOSED

The Annual report is fundamentally an asset register; PPM, OHS critical-equipment, and service-cost KPIs all read from it. Build it first (P1).

D3 — OHS Act compliance % is separate from electrical COC PROPOSED

Mirrors the Site-Health redesign rule (COC ≠ operational health). OHS % is its own weighted rollup; COC remains the legal-certification fact. Weights live in one named constant.

D4 — Reuse the inspection engine for building condition PROPOSED

Add condition + action_timeframe fields and seed new templates rather than building a second inspection system. Action items flow through the existing snag pipeline.

D5 — Commercial domains are import-only in v1 PROPOSED

Trading, leasing, arrears, footfall and toilet-fund are the centre manager’s data, outside WM’s engineering capture. Display via Excel import (CM Page 2); native capture deferred. Keeps the engineering build unblocked.

D6 — New module named “Fortress Building Report Pack”, distinct from the electrical FORTRESS template PROPOSED

Avoids the naming clash with fortressTemplate.ts (electrical scope-of-works). Consider renaming that template to “WM Electrical Scope” to remove ambiguity.

D7 — One pure KPI module per score, screen + PDF both call it PROPOSED

Extends the Site-Health SoT pattern: buildingCompliance.ts, ppm.ts, utilities.ts as unit-tested pure functions. No divergent calculators.

Open questions (need Arno)

  • Scope mandate: is WM delivering the full Fortress pack (incl. commercial), or the engineering/compliance + condition slice with commercial imported? (drives D5)
  • Capture vs import: for tenant/turnover/utilities, native data entry in-app, or Excel import to start? (the Excel layouts are stable templates — import is cheap)
  • One building = one site? Confirm no multi-report-per-site cadence conflicts (OPS monthly, CM monthly, Annual).
  • OHS weighting: who owns the section weights for the compliance %? Is the OPS header’s 85/10/5 split the formula, or illustrative?
  • Live schema: can you run (or grant) a read-only pull of the prod sites/subsections/snags schemas to gate migrations?
DID / ASSUME / RECOMMEND.
DID: reviewed the existing spec set + 3 Fortress workbooks; mapped 17 domains to the current build; produced this gap analysis, a per-building dashboard (real Abaqulusi data), a 38-KPI catalogue, a data-model delta and a 6-phase plan. Nothing built or migrated.
ASSUME: buildings = sites; WM’s core is engineering/compliance/condition; Excel layouts are stable enough to import; the Site-Health redesign lands first. System-reference docs are partly stale (flagged).
RECOMMEND: confirm scope (D5) + capture-vs-import, then start P0 audit and P1 asset register. Park commercial capture until the engineering spine is in.
